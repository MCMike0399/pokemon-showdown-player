# Campaign c10 persistent M5 development and live confirmation

Protocol fixed 2026-10-22 before c10 training or gate results. The objective is
an Elo improvement, not GPU utilization or an improvement in predictive loss
alone. This campaign runs alongside c9 and never replaces its active test.

## Candidates and training

**Preview candidate.** Keep the incumbent pvalue-661448b6a320fce0 model. Among
legal plans within .025 of its best probability, subtract `.04 * min(1, N/2)`
per Intimidate lead, where N is the number of opposing preview species among
Kingambit, Milotic and Annihilape. Select the highest adjusted score. The
adjustment uses only public preview species and our own known abilities. It
does not force a particular bring, ban Incineroar, or change turn search.
Missing information falls back to the incumbent preview.

This is a bounded experimental prior motivated by the c9 matchup audit. It
is not assumed correct: Kingambit and other targets can still lose to Incineroar,
and species in the six need not lead or have the assumed ability.

**Learned-screening/endgame candidate.** Train one new screening model on the
newest at most 2,000 completed games under the incumbent's baseline policy key,
excluding every A/B game with an enabled experimental factor. Minimum 500 games.
Freeze the file list and hashes before training. Newest 30% of these games are
a chronological test; split the remainder 85/15 by game hash into train/validation.

Use the existing 128×128 screening MLP, AdamW lr .002, decay .0001, batch4096,
30 maximum epochs, patience4, seed20261101. MPS only qualifies this branch;
a CPU fallback remains recorded but does not qualify. Allow half the MPS
recommended working set, the full selected dataset and swap as requested.

Choose prefilter sizes on validation only: own recall ≥.90, final-choice
survival ≥.98, opponent recall ≥.92. Test data may reject the fixed sizes but
never enlarge them; allow the existing .03 test tolerance, at least50 test
groups per side and300 validation groups per side. Both estimated validation
and test savings must be ≥15%.

If those checks pass, the candidate combines the trained prefilter with
`endgame_d2 {alive:2, top_ours:4, top_opp:4, keep:8, probes:2}`. Its purpose is
to spend less on screening and more on selected endgame decisions. It must
pass a superiority test for wins. This is a new combined strategy; it does
not relax the older 20% saving threshold for a screening-only promotion.

## Frozen offline experiment

Both candidates use the exact live team and incumbent pvalue preview, with
the pinned c5 configuration as their base. Only the named candidate options
differ. C9 may later promote boost; c10's final live test then compares both
arms against that new live baseline rather than promoting from old offline data.

Each candidate gets one 800-pair pooled stage, alpha .05, rejecting at400 or600
complete pairs if gains ≤ losses. No early success; the final exact paired sign
test must pass. Seeds:20261101 for preview,20261102 for endgame. Errors retain
the same seed, at most three attempts; exhausted errors void the pair. The
first stopping decision is final, and already-running late results are retained
but excluded. Neither candidate is retuned or restarted on fresh seeds after
a rejection.

The opponent alternates by pair between the frozen argmax human imitation
(`human-449e6bd0e8869deb`, preview `preview-1455f4a55d18112a`) and the incumbent
search. Both pilot the same fixed real-team pool and get the same seeds in both
arms. This diversifies the offline opposition; it is not claimed to reproduce
human behavior. Offline success is only a filter for fresh ladder confirmation.
Asset hashes and the source commit are stored in the campaign spec.

## Hardware and persistence

Use eight concurrent offline games total, four per candidate, one simulator
engine per searching agent. MPS training uses two CPU threads. There is no
free-RAM or swap-based admission cutoff for this campaign. The existing live
priority mechanism pauses the registered offline process groups during live
search and resumes them afterward. This lets background work use the machine
while the ladder opponent is thinking. The existing 150 GB data budget remains
in force; no new self-play corpus is generated by this campaign.

Run the supervisor as `dev.pokemon-showdown.campaign-c10`, with launchd
RunAtLoad/KeepAlive and a process lock. Source is pinned in `<checkout>.c10`;
runtime data stays under `data/ml/value/campaign-c10`. A restart adopts live
worker PIDs or resumes the same result ledger, never a second copy. A worker
with three failed starts stops for inspection rather than silently changing
the experiment. Hash mismatches also stop scheduling.

After training, run a clean-checkout promotion preflight (tests, source secret
scan and push authentication) before launching long gates. Stage only the
immutable screening JSON needed by those tests; do not attach mutable live data
to the test checkout.

## Fresh live test and promotion

Wait until c9 is inactive. Never replace any other active campaign or its arm
ledger. If neither offline candidate passes, finish without a live change.
Otherwise merge the options of the offline winners in fixed candidate order
and create **one** new live A/B, id `c10`, factor `upgrade`. This directly tests
the combined upgrade against the current baseline; offline main effects are
not assumed to add together.

Use balanced two-game blocks, seed20261201, and the existing SPRT of 0 versus
+40 Elo, alpha .05/beta .10, minimum300/maximum3000 games. Reject or inconclusive
means no promotion. H1 permits the existing `ab_watch.py` path to test, scan,
commit, push and gracefully deploy the exact options. No offline-only promotion.
The live worktree must contain the pinned campaign code before the A/B starts.

An unattended reboot resumes the supervisor after login; it cannot bypass
FileVault's login requirement. No second Showdown account or player is created.

## Operations

```bash
.venv/bin/python scripts/campaign_service.py install
.venv/bin/python -m search.campaign status
.venv/bin/python -m search.ab_test status
tail -30 data/ml/value/campaign-c10/supervisor-errors.log
```

`state.json` records phase, worker IDs, attempts, timestamps and errors. Gate
ledgers are `preview.jsonl` / `endgame.jsonl`; final results have `-result.json`.
`live/` holds the eventual A/B watcher outcome. The spec permits only `active`,
`slots` (even2..8) and `poll_seconds` to change without a new protocol. Setting
`active:false` pauses new scheduling; already-running jobs keep their evidence
and finish. Do not edit the pinned worktree while it is running.

Success is a positive live SPRT followed by a stronger Elo performance segment.
There is no promise that either candidate wins. If both fail, the campaign
records that result and idles instead of retraining on the same evidence forever.
